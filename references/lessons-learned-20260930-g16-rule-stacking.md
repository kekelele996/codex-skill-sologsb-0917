# 2026-09-30 G16 废弃复盘：单子系统规则堆叠

本文件记录 2026-09-30 一次真实的 G16 废弃案例（`#19738`，项目 `sologsb-1020 · 档案元数据核对台`），
以及为此在 1.8.2 里加的 `complexityTopology` 门禁。出困难或地狱题之前必须读完这一页。

## 一、废弃事实

- 案例编号：`#19738`；项目：`sologsb-1020 · 档案元数据核对台`；自评难度：`困难`。
- 平台判定规则：`G16`（题目难度达不到「困难」）。
- 平台判定原文（关键一句）：**“需要在既有核对子系统内实现多项规则，约束明确、没有架构级设计取舍”**，
  真实难度判为「中等」，三项特征“多模块整合、关键设计取舍、复杂技术关注点”一项都没有体现。
- 数据状态：作废且不可返修。难度是题目本身的属性，改写措辞或调高难度字段都无效。

题面覆盖的功能：两套核对口径切换、未决分数失效重算、历史结论保留、关键冲突说明、批量跳过、
本地保存、撤销重做、导出。功能数量看起来不少，题面读起来也很完整，但平台仍然判中等。

样本已并入 `references/g16-discarded-samples.json`（`id=19738`，`shapeTag=单子系统规则堆叠`）。
该样本的 `userPrompt` 由跨设备案例转述重建，`sourceNote` 里写明了取不到原始 submission 的原因；
取到原文后应逐字替换。

## 二、为什么这些功能不算困难

1. 所有规则都落在同一个核对子系统内部：口径、分数、结论、冲突说明、跳过、保存、撤销、导出都是
   这一个前台工具的状态，只有一个所有者，没有第二个系统或岗位各自持有状态。
2. 没有跨模块不变量：换一套口径后失效重算，只是把本地派生状态重算一遍；旧的确认结论保留，
   也只是本地留痕，不影响任何外部系统的结果。
3. 没有设计取舍：口径怎么切、什么时候重算、跳过哪些条目、导出什么字段，都是可以照着条款逐条实现的
   确定性规则，不需要决定事实来源、事务边界、版本策略或恢复方式。
4. 没有失败或恢复链路：唯一的“异常”是本地重算，错了再算一次即可，不涉及跨侧对账、补偿或回滚。

一句话：**规则族的数量不等于难度**。把十条本地规则排在一起，仍然是一条本地规则的十次重复。

## 三、六个规则族（机器识别的信号）

`scripts/prompt_tools.py` 里的 `RULE_STACK_FAMILIES`：

| 信号族 | 命中示例 |
| --- | --- |
| `mode-switch` | 两套/多套核对口径、标准、模板之间的切换 |
| `recompute-invalidation` | 失效、重算、作废、过期、重新确认 |
| `history-retention` | 历史结论、旧版本、旧记录的原样保留 |
| `conflict-gate` | 冲突、拒绝保存、拦截、闸门 |
| `batch-operation` | 批量、一键、整批、逐条 |
| `persist-undo-export` | 本地保存、撤销、重做、导出 |

命中四个以上（`RULE_STACK_THRESHOLD = 4`）即视为“单子系统规则堆叠”，`validate_difficulty_review`
直接阻断。这条规则不是判难器：命中本身不代表题面不够难，而是要求补一份能核对的跨边界拓扑；
没命中也不代表题面就够难。

## 四、complexityTopology 要求

命中四个以上规则族后，`workspace/评审文件/难度论证.json` 必须提供 `complexityTopology`，
六个字段缺一不可：

| 字段 | 要求 |
| --- | --- |
| `kind` | 只允许 `跨系统对账`、`失败恢复`、`迁移兼容`、`并发冲突`、`权限边界`、`容量约束`、`离线合并`、`独立所有权拆分`；英文别名同样可用 |
| `promptQuote` | 题面原句（≥12 字），且本身要体现该跨边界关系 |
| `stateOwners` | 至少两个，名称必须出现在题面原文里 |
| `failureOrRecovery` | 失败、恢复或补偿发生在哪一侧（≥20 字） |
| `whyNotLocalRuleList` | 为什么它不是本地规则表（≥30 字） |
| `negativeOutcome` | 拓扑错了的可见后果（≥12 字） |

两条硬约束：

1. **`state-invalidation` 不是合法拓扑类型**。只有“口径更新后失效重算”不能证明困难，
   它是规则堆叠的第一族，写成拓扑会被单独报错。
2. **`promptQuote` 必须匹配所声明的跨边界模式**。引一句和跨边界无关的题面（例如“关键冲突要写清来源”）
   即使是原句也会被报错。

## 五、正确改写边界

- 可以保留原来的业务场景和大部分规则，但必须把状态所有权真正拆开：让两个系统、部门或岗位各自持有
  自己那份状态，任一侧更新只影响本侧，另一边靠对账收口。
- 必须给出失败后的按侧恢复路径（保住上一版结果、重试、以哪一侧为准），而不是本地重算。
- 题面里要能读到这个跨边界关系：出现两个状态所有者的名字、对账或恢复的原句、冲突来源的说明。
  这些原句随后要原样写进 `complexityTopology.promptQuote` 和 `stateOwners`。
- 不能靠加规则、加按钮、加导出格式、加撤销重做来通过门禁。凑不出真实跨边界拓扑时，
  题目应当降到中等或者换题，而不是继续在同一个子系统里堆条款。

正反例（同一件事的两种写法）：

> 反例：核对台补两套口径切换，口径更新后未决分数失效重算，历史结论保留，冲突写清原因，
> 支持批量跳过、本地保存、撤销重做和导出。

> 正例：档案室和整理室各有一套编目基准，整理室先给未决分数、档案室确认后才落定；
> 任一基准更新后只重算受影响的那一份，对账失败后保住上一版结果并按侧重试。

## 六、出题前的自检

写完题面先问三句话：

1. 这道题里有没有两个各自持有状态的系统、部门或岗位？只有一个就是本地规则堆叠。
2. 错了以后是谁承担后果？只在本地重算就是中等，必须能说出跨侧对账或按侧恢复。
3. 把 `complexityTopology` 的六个字段都填出来，是否每一条都能在题面里找到对应原句？
   找不到就是在自证，`prompt` 阶段会被阻断。
