# GSB 文案编写通则（2026-09-21 起，2026-09-23 修订）

本文件是 `GSB 理由` 的唯一写作口径，适用于所有题目，不针对某一个提示词。
机器可判定的部分由 `scripts/gsb_tools.py` 与 `submission/scripts/preflight.py` 阻断；
其余部分按本文件的正反例人工对照。

## 一、总原则

- 写事实，不写判断词：谁在什么环节做了什么、结果是什么，让读者自己得出结论。
- 朴实但不干练：读起来像同事口头复盘，不像公告或提纲；不能为了短而砍掉语气和结果。
- 一句一个事实，句子之间有推进关系；结论句只出现一次。
- 全文只讲与胜负相关的事，不复述代码审计。

## 二、用词

- 用口语常用词，不用生造简写和行业黑话。维护词表见 `references/reason-word-replacements.json`。
  - 反例：`落库`　正例：`入库`
  - 反例：`闭环`　正例：`完整覆盖`
  - 反例：`根因`　正例：`原因`
- 同一主体前后统一称 `A 侧方案`、`B 侧方案`，不使用省略单字或「前者/后者」。
- 业务名词写完整：`匹配规则`、`命中计数`、`默认响应`，不写成 `规则表`、`计数`、`默认`。
- 不加「真实」「真实用户」「实际用户」「真正」「其实」「本质上」这类空转词；机器校验对「真实」等表达给出警告。
- 常用命令不原样照抄，`npm run build` 统一写为 `build`；这类命令在历史理由中反复出现，容易触发公共长片段去重。

## 三、句式：把语气与结果补足

动词后面要把状态和结果交代清楚，不要写成电报式短句。四组基准对照：

| 过于干练（反例） | 朴实（正例） |
| --- | --- |
| 在服务层给匹配规则建独立表 | 在服务层给匹配规则建了独立表 |
| 读库时发现停用位被默认值盖掉 | 读库时发现停用位被默认值覆盖掉了 |
| 开关保存后两条规则照旧读回 | 开关保存后两条规则还是照旧读回 |
| 计数 2 变 22 | 计数从2变22 |

同类可用的补足手段：`还是`、`仍然`、`已经`、`随后`、`后来`、`之后`、`各加一`、`多搬了一趟`。
补语气不是灌水：不许新增没有证据的形容、评价和结论。

## 四、排版

- 数字、英文与中文之间不留空格：写 `计数从2变22`、`APIs.vue的回调`；
  唯一例外是两个固定称谓 `A 侧方案`、`B 侧方案`。
- 严格使用纯文本，禁止任何 Markdown：无标题、列表、代码块、行内代码、表格、引用、链接、图片、强调标记和 HTML 标签。
- 不粘贴命令与报错原文；确需给可核对点就写文件名、函数名或接口状态。

## 五、内容结构

- A、B 两侧都要分别写过程与产物：
  - 过程 = 动作 + 定位点（在哪个环节、哪个文件、哪条需求上做了什么）。
  - 产物 = 可观察结果（返回、保留、为空、归属、失败、通过）。
- 负面判断必须写清触发节点与客观后果：触发节点落到步骤、文件、命令或需求；
  客观后果写「没有写入」「读回为空」「回退默认响应」这类可见结果，不能只写「随后通过」。
- 结尾前先用一句话交代这题最看重什么，再给结论，例如「这题最要紧的是并发保存不丢数据，因此选择 B 侧方案」。
  只罗列事实后直接宣布胜负，平台 AI 化打分会记为“没有交代判准”。
- 结尾只收束一次，直接说明谁更好。

## 六、禁止项

- 录屏、视频、截图、浏览器、测试设备、运行环境、验收宿主、Otty、鼠标、分辨率等场外因素只能作为附件证据，不得写进理由，没有例外。
- 不在候选容器内生成、而是在本地（容器外）编写、添加或放置的测试文件、测试脚本、自测脚本和验收脚本同样属于场外因素，不参与 GSB 文案编写，不得作为过程或产物依据写进理由。这里的“本地”特指非容器内生成，即不是候选容器运行过程中产生的文件或脚本。
- 不得引用 `evaluationExcluded` 的环境或工具噪声证据，也不得把其他工具噪声当成独立评分项或胜负依据。
- 不用测试或断言数量堆砌（不写「10 个测试」「12 项断言」），改写业务覆盖描述。
- 不用三位以上机器式序号；不写「第一步」「第二步」这类流程编号。
- 不做主观拔高：`更细`、`更稳`、`更贴合`、`持平`这类词不能单独支撑判断。

## 七、长度与自检

- 全文 150–240 个非空白字符；A、B 两侧必须都被明确覆盖。
- 交稿前逐条自检：
  1. 有没有生造简写或黑话（`落库` 一类）。
  2. 数字、英文两侧有没有多余空格。
  3. 每句是否补足了语气与结果，读起来像人话。
  4. A、B 两侧是否都写了过程与产物。
  5. 负面判断是否同时写了触发节点与客观后果。
  6. 有没有混入录屏、截图、测试数量等禁止项。


## 2026-09-22 返修补充

- 禁止用中文念法或缩写代称提交号，例如“依六四二四七二c”。需要指代发布结果时写原有业务值或代码值，如 `status`、`paidAt`、订单号或接口路径。
- 负面判断的触发节点不能只写“首次运行阶段”。要写打开哪个页面、点击哪个入口、调用哪个接口、执行哪条命令、命中哪个文件或看到哪条报错。
- 不要把现象压成“前置值条件更新”“先查后存模块”这类名词串，也不要把读数依次码好当结论。先写触发动作，再写现场现象，最后写客观后果。
- 并发类问题要把“同时做什么、出现什么结果、结果怎样影响业务”完整展开；不能只写“四十次付款生成七条记录”后直接宣布胜出。

- 低相似度查重只在整段相似度达到 20% 时进入复核；低于 20% 且没有 8 字以上公共长片段时，不因零散短词重合误伤自然复盘。公共长片段、模板 n-gram 和高相似度仍然硬阻断。


## 2026-09-23 自然度修订

平台“理由 AI 化打分”对已通过记录的点评：句子偏电报体，多句以「A 侧方案」起头，
只罗列事实、没说清最看重哪一条。下面几条由 `reason_flow_errors` 阻断：

- 相邻两句不要用同一个称谓起头。同一侧的几件事连成一段说，后一句直接接着讲，或用「随后」「这一改动」承接。
- 每侧称谓「A 侧方案」「B 侧方案」最多出现 3 次。
- 不写 8 字以下的碎句，例如补在末尾的「来自接口返回。」。

写法上按“一侧一段话”组织：先说这一侧做了什么，再说结果怎样，最后一句把两侧拉到同一个判断标准上比较。

反例（清单式，每句一个事实）：

> A 侧方案验证并发保存只成功一次。A 侧方案发布时先锁行再生成快照。A 侧方案登录请求遇404。B 侧方案在验证时补跑HTTP并检查回读。

正例（按侧成段，交代判准）：

> A 侧方案在发布时先锁行再生成快照，并发保存也只成功一次。可打开api.ts时多拼了一层前缀，登录请求一直返回404，页面进不去日记。B 侧方案验证时补跑了接口并回读结果，登录、存草稿和发布都能走通。这题最要紧的是入口能用，因此选择 B 侧方案。

语气词和承接词要少量、自然地用，不要为了过检查去堆「了」「还是」「已经」。

## 与交付完整性描述的分工

- GSB 理由写两侧对比：过程加产物，最后给判断。
- 交付完整性描述只写各自一侧的完成度，规则见 `references/delivery-scoring.md`。
- 两者可以提到同一件事，但描述不许照抄理由的句子。
