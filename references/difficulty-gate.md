# G16 困难难度门禁

## 触发来源

2026-09-29，提交 `#19090`（`sologsb-1106 · 木版年画刻版工序档案`）被 SOLO2 以
`G16 · 题目难度达不到「困难」` 废弃。平台认定：规则虽然多，但都落在同一个业务域的
批次登记、状态标记和页面展示里，逐条写清后可以顺序实现，没有多模块整合、关键设计取舍或复杂技术关注点，
真实难度只是中等，并且题目本身不可返修。

这个案例说明：**规则数量、字段数量、页面动作数量、测试数量、代码改动量，都不能证明题目困难。**
困难难度必须从题目本身可以推导出，不能靠措辞把中等题包装成困难题。

## 硬门槛

困难或地狱题必须同时满足：

1. 至少列出两个互相独立的困难轴，不能把同一件事拆成两个标签。
2. 至少一个困难轴属于 `multi_module`、`design_tradeoff` 或 `complex_state`。
3. 所有困难轴合计至少能落到三个不同的源码锚点，避免单文件或单页面的小问题冒充困难题。
4. 每个困难轴都写明提示词中的原句、为什么不能按顺序直接实现、失败时的客观后果。
5. 写出一道可以区分的中等题反例，证明本题没有停留在那个边界内。

允许的困难轴：

| 标识 | 含义 | 必须证明什么 |
| --- | --- | --- |
| `multi_module` | 多模块整合 | 至少三个模块/数据层/入口共同参与，修改一处会牵动另一处 |
| `design_tradeoff` | 关键设计取舍 | 两个做法各有代价，必须给出业务优先级或冲突处理结果 |
| `complex_state` | 复杂状态 | 多状态、历史快照、软删除、重放、版本或跨记录一致性 |
| `concurrency` | 并发 | 同一资源被多处同时修改，或需要幂等、锁、冲突恢复 |
| `compatibility` | 兼容性 | 旧数据、旧接口、旧格式、旧协议与新增行为必须共存 |
| `permissions` | 权限 | 不同角色或边界下的允许/拒绝，且失败不能绕过 |
| `performance` | 性能 | 有明确规模、时延或资源边界，普通遍历会失败 |
| `exception_recovery` | 异常恢复 | 中断、失败、回滚、补偿、恢复任务或部分成功链路 |
| `migration_consistency` | 迁移一致性 | 结构升级或数据搬家前后旧记录、引用和约束仍一致 |

建议组合：

- 好组合：`multi_module + migration_consistency`；
- 好组合：`design_tradeoff + concurrency`；
- 好组合：`complex_state + exception_recovery`；
- 不合格：`design_tradeoff` 单独出现但没有第二个独立困难轴；
- 不合格：两个轴都只是同一页面的字段校验、提示文案或按钮状态。

## 容易被误判为困难的题

以下内容单独出现时通常仍是中等题：

- 给页面增加一个筛选、排序、分页或导出按钮；
- 给表单增加一组必填校验、数值上限或错误提示；
- 增加一个状态枚举和“符合条件才能提交”的判断；
- 在一个页面里同时显示几个统计数字；
- 改动一个数据字段、一个映射表或一份文案；
- 规则有十条但每条都能按顺序写成 `if/else`；
- 测试多、文件多、改动行数多，但都围绕同一个线性流程。

把这些动作写长、写细或增加测试，不会提高真实难度。

## 可作为困难的题

只有满足至少一个强困难轴，并且题面必须描述其约束和后果时才可用：

- 多模块整合：登记动作要同时改变业务记录、持久化事务、历史档案和另一个页面的可见状态，
  任一处失败都不能留下半成品；
- 关键设计取舍：同一份数据既要支持离线继续编辑，又要在恢复联网后合并冲突，
  必须明确以哪一侧为准以及如何保留另一侧的修改；
- 复杂状态：旧记录保留快照、重做、撤销、作废、替代关系和历史版本，任何一步都不能把旧关系弄断；
- 并发：两个终端或两个标签页同时提交，只能有一个写入，另一个必须拿到可恢复的冲突信息；
- 兼容/迁移：旧版本数据没有新字段，升级后仍能读、算、导出，并且不能被错误地当成新记录处理；
- 权限：不同角色看到和能执行的动作不同，越权请求必须被拒绝且不能改变数据；
- 异常恢复：写入分多个阶段时，失败后能补做、回滚或重试，不能只成功一半；
- 性能：数据量或响应时延有明确边界，不能用一次性全量扫描绕过。

## 必须提交的难度证明

在写提示词前建立 `difficulty-audit.json`，再把文件绝对路径传给：

```bash
python3 scripts/sologsb.py prompt --task-root ROOT \
  --task-type feature迭代 --difficulty 困难 \
  --candidate CANDIDATE --review REVIEW \
  --difficulty-audit DIFFICULTY_AUDIT
```

证明文件模板见 `references/difficulty-audit-template.json`。`sourceAnchors` 使用相对
`source/origin` 的真实源码路径，至少三个不同锚点。`promptQuote` 必须逐字出现在最终提示词里。
校验失败时 `init` 不进入 `prompt_ready`。

## 自检问题

提交提示词前逐条回答：

1. 如果只改一个页面、一个文件或一个字段，能不能完成？能，则通常是中等题。
2. 哪个模块会因为另一个模块的改动而失效？题面有没有把这个连锁关系写出来？
3. 有没有两个实现都合理、但代价不同的选项？优先规则是否明确？
4. 是否有旧数据、并发操作、异常中断、权限边界或性能边界？
5. 如果去掉所有测试和验收话术，题目本身是否仍然需要设计？
6. 能否用一段稳定的 `if/else` 代码就完成？能，则不要标困难。
