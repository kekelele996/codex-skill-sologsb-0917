# G11 改动量与仓库洁净门禁

## 触发来源

2026-09-19，提交 `#1952`（`cy-406 · 合同模板在线编辑器`）被 SOLO2 以 `G11`
废弃，平台返回 `A 改 0 行，B 改 0 行`。因此后续提示词设计和提交预检都要同时约束
实际业务改动量与产物仓库洁净度。

## 提示词设计要求

- `困难` 题的建议目标是每侧至少 `30` 行非测试业务代码改动，并跨至少 `3` 个业务文件。
- 本地绝对底线是每侧至少 `10` 行非测试业务代码改动。
- 提示词必须让改动自然跨数据模型、持久化或事务、业务 Store/Service、页面或入口中的多个层次。
- 测试代码、文档、锁文件、依赖目录、构建产物、缓存和纯配置文件不计入改动量。
- 不能为了凑行数增加无关重构、格式化、注释或重复代码。改动量仍要服务于同一个业务问题。
- 如果基线无法支撑上述改动量，应更换题目或提高真实冲突复杂度，而不是降低质量。

## 发布阶段

- 产物 commit 生成前必须排除依赖目录、构建产物和缓存。
- 锁文件随依赖清单发布：模型改了 `package.json`、`go.mod`、`Cargo.toml` 等依赖清单时，同目录（或工作区根目录）的锁文件一起进入产物 commit；`go.sum`、`go.work.sum` 改了就发布；清单没改时锁文件照旧撤回。
  锁文件不计入改动行数。规则实现在 `scripts/common.py` 的 `paired_lockfiles`，发布与提交预检共用。
- 发布阶段仍为 A、B 分别生成本地产物 commit 和远端快照，不因少于 `10` 行提前停止。
- 每侧必须写入 `lineGate` 记录，包含初始快照、产物快照、业务代码行数、业务文件列表和门禁状态。
- `publish` 完成后写入 `monitor/change-volume-line-gate.json`。低改动量记录为 `failed`，
  但只有提交预检阶段才执行最终阻断。
- 少于建议的 `30` 行或不足 `3` 个业务文件时给出警告。
- A/B 任一产物差异中出现 `node_modules`、`dist`、`build`、`coverage`、`.next`、`.nuxt`、
  `.vite`、`target`、`vendor`、`__pycache__`、虚拟环境，或没有配对依赖清单改动的锁文件时阻断提交。
- 本地预检是平台 `G11` 的保守近似，不能替代平台最终质检；平台判定为准。

## 提交阶段

- 预检从远端 `main` 初始快照与 A/B 产物 commit 复算业务代码改动量。
- 任一侧少于 `10` 行时写入 `workspace/评审文件/pre-submit/change-volume-review.json`，
  并把 `change-volume-line-gate` 作为例外审批类型写入 `submission-payload.json`。
- 只有当低改动量是唯一阻断项时，才允许设备配置里的审批人批准
  `change-volume-line-gate` 例外。
- 例外审批必须同时绑定当前 payload 哈希、交付表哈希和改动量复核包哈希。
- 仓库存在依赖、构建、缓存或未配对的锁文件时，以及其他任何门禁失败时，都不能使用该例外。
- 正常流程在完整审核通过后自动由设备配置里的审批人记录批准，并直接执行
  `submit --task-root ROOT --execute`，不需要人工审批文件。

## 2026-09-23 锁文件修订

旧规则把锁文件和依赖目录一起排除。250 个已发布的 A/B 里，有 36 个是模型改了依赖清单、锁文件却没推：
例如 `cy-387` 的 A 推了 `frontend/package.json`，没推 `frontend/package-lock.json`，从 GitHub 干净检出后 `npm ci` 直接报错。
复核从 GitHub 检出代码，这类失败会被算到模型头上，写进 GSB 理由和交付完整性描述。

锁文件排除是技能自己加的规则。`#1952` 被 G11 废弃的原因是产物里混进了 `node_modules` 和 `dist`，平台统计为 0 行，与锁文件无关。
