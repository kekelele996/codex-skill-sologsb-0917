# GSB 证据与文案

## 证据索引

自动化检查无法表达但已人工复核的产品事实，可以写入任务目录的 `monitor/custom-evidence.json`。
每次 `audit` 都会重新合并该文件；过程证据必须带 `trace` 锚点，产物证据必须带 `artifact` 锚点，且 ID 不能与自动证据重复。自定义证据只能记录真实的产品、接口、数据、构建或需求事实，不能用来包装环境或工具噪声。

`monitor/evidence.json` 中每条证据至少包含：

```json
{
  "id": "A-process-001",
  "side": "A",
  "type": "process",
  "polarity": "negative",
  "text": "可读事实",
  "evaluationExcluded": false,
  "trace": {
    "sessionId": "...",
    "eventIndex": 12,
    "eventUuid": "...",
    "quote": "...",
    "toolName": "Bash"
  },
  "artifact": null
}
```

产物证据的 `artifact` 包含 commit、路径、行号、命令、退出码和输出摘要。
过程、产物证据不能混用。任何最终文案引用的事实都必须存在至少一个证据 ID。

## 结论

- 先判断数据有效性；工程故障或环境未重置标为无效，不能强行比较。
- 优先比较最终业务结果。模型生成的产物无法构建、启动或满足需求时是真实扣分。
- 只有两次互有优劣且对业务结果无可验证影响时才选 Same。
- A/B 两侧都要写好在哪、不好在哪，并且每侧都覆盖过程与产物；过程写触发节点、实际行为、返工或修正，
  产物写文件名、报错、可观察行为或未实现需求。不能只写交付物毛病，也不能只写执行动作。
- 整个 `GSB 理由` 强制 150–240 个非空白字符。
- `GSB 理由` 必须严格使用纯文本，不得包含任何 Markdown 语法；标题、列表、代码块、行内代码、表格、引用、链接、图片、强调标记和 HTML 标签均阻断。
- `GSB 理由` 不得引用录屏、视频、截图、浏览器、测试设备、运行环境、验收宿主等场外因素，没有例外；不在候选容器内生成、而是在本地（容器外）编写、添加或放置的测试文件、测试脚本、自测脚本和验收脚本同样不参与 GSB 文案，不得作为过程或产物依据。这里的“本地”特指非容器内生成，即不是候选容器运行过程中产生的文件或脚本。
- `evaluationExcluded=true` 的环境或工具噪声证据不能被 claim、sentenceEvidence 或理由正文引用。
- Same 也必须写每侧过程与产物事实，再写等价点和相互抵消点。
- 完成后走固定版本 `ra-人话` 并生成审核 JSON，最多重写三轮。
- G10 本地门禁：与当前 GSB 只读列表比较，精确重复或长连续片段复用直接阻断。

## 过程与产物双层覆盖

`GSB 理由` 不是只评价 A/B 交付物本身，还必须同时覆盖过程与产物；A、B 两侧都要各自覆盖两层。
过程层回答“模型在原生轨迹中实际做了什么”，产物层回答“这些动作最终交付了什么结果”。

- 过程层必须来自轨迹证据，至少写清执行事实与定位节点：在哪个步骤、文件、命令或需求触发，
  读取、检查、修改、执行、排查或返工了什么。只写“进行了测试”“做了迁移”“改过服务”
 不能算过程。
- 产物层必须写清最终可观察结果：接口返回、页面或交互、数据处理、写入结果、缺失字段、
  构建或启动结果、需求覆盖和真实失败。只写“完成了需求”“结果更好”不能算产物。
- 同侧两层最好形成因果链：过程动作说明问题是在哪个环节产生或被发现，产物结果说明它最终
  造成了什么可验证差异。
- 写过程前先回轨迹回答四个问题：读过或检查过哪些相关文件；实际修改或创建了哪些文件；
  在哪个步骤发现问题、修正或返工；有没有走过弯路。能回答一项就写真实的一项，不能凭印象补。
- `claim.text` 是理由锚点，不是只供内部审核的备注。草稿中用于支撑该侧过程/产物的
  `claim.text` 必须原样出现在 `GSB 理由` 中。
- 录屏、视频、截图、浏览器、测试设备、运行环境、验收宿主、Otty、Terminal.app、鼠标、分辨率、终端窗口仍只能作为附件证据，
  不得作为过程或产物好坏的依据，也没有任何例外；不在候选容器内生成、而是在本地（容器外）编写、添加或放置的测试文件、测试脚本、自测脚本和验收脚本同样不得作为过程或产物好坏的依据。
- 禁止使用“落在……”式收束句式；结论直接写“因此选择 B 侧方案”或“B 侧方案更好”。

### 2026-09-20 真实打回

平台打回原因：整段只写“升级迁移里旧唯一约束没有去掉”“索引列表仍含
`idx_run_input_version`”“接口返回少了字段”和需求覆盖情况。这些都属于产物层；
没有交代模型在过程中读取了哪些文件、修改后才发现约束问题、是否走过弯路，因此判定
“过程与产物未同时覆盖”。

被判定缺少过程的原因不是文章短，而是所有事实都落在最终交付物。修复时不能只补一句
“过程中进行了检查”，必须回到该侧轨迹，提取至少一个真实执行事实。

返修骨架（方括号内容必须替换为本次轨迹和 diff 中的真实事实）：

```text
A 侧方案在[具体步骤/命令/文件]时[读取、检查、修改、排查或返工动作]，但[实际过程问题]；
最终[旧唯一约束未移除/索引仍含某标识/接口缺少某字段等产物结果]。
B 侧方案在[具体需求或步骤]时[实际动作]，最终[可观察产物结果]。
```

如果轨迹确实显示模型读取过 `database/init.sql` 与迁移脚本，可以写成：

```text
A 侧方案在联调阶段读取 `database/init.sql` 和迁移脚本后，仍保留了旧唯一约束，
升级后索引列表仍含 `idx_run_input_version`，接口返回缺少版本字段。
```

如果轨迹没有这条动作，禁止照抄示例；应换成轨迹中真实存在的读取、修改、验证或返工事件。

## 负面评价触发节点硬门禁

每条 `polarity=negative` 的 claim 必须同时提供 `triggerKind`、`trigger` 和
`objectiveConsequence`，并让 `trigger` 与 `objectiveConsequence` 都原样出现在 `GSB 理由` 中。
只写“过程中”“操作时”“某一步”“存在一个问题”等泛化描述，校验直接失败。
`triggerKind` 只能取以下四类：

- `step`：具体步骤、轮次或阶段，例如“第二次执行测试时”“初始化阶段”“联调阶段”；
  只写“第一次操作时”仍不合格，序号后必须说明执行了什么操作。
- `file`：具体文件或路径，例如“修改 `config/database.yml` 时”“`src/order/service.go` 第 42 行”。
- `command`：具体命令或工具调用，例如“执行 `go test ./...` 时”“第二次 Bash 调用时”。
- `requirement`：触发问题的需求或操作，例如“新增指标时”“编辑指标时”“重命名指标时”。

触发节点必须能定位到已引用 evidence 中的步骤、文件、命令、需求或对应产物。

反例与改写：

- 不合格：“A 侧过程里曾把工作目录写错一次。”
  原因：`过程里` 不是触发节点。
- 合格：“A 侧第二次执行 `go test ./...` 时，Bash 的工作目录落在仓库外，导致包路径解析失败。”
- 不合格：“B 侧只同步口径说明和默认单位。”
  原因：没有说明是新增、编辑还是重命名指标。
- 合格：“B 侧在新增指标时，只同步了口径说明和默认单位，新增、编辑和重命名流程没有接入。”

触发节点是负面评价的最低要求，不能替代实际行为、客观后果和 evidence 绑定。

负面 claim 的写法：

```json
{
  "side": "A",
  "type": "process",
  "polarity": "negative",
  "triggerKind": "file",
  "trigger": "修改 culture_recipe_service.go 时",
  "objectiveConsequence": "修改没有落地",
  "text": "A 侧方案在新增指标时只同步了口径说明和默认单位，新增、编辑和重命名流程没有接入，提交后配置没有写入。",
  "evidenceIds": ["A-process-error-0323"]
}
```

`objectiveConsequence` 必须写实际影响，不能只写后续改善。例如“后续构建通过”不构成负面后果；
应写成“修改没有落地，构建一开始无法包含该处改动”。`Same` 也必须让每条负面 claim 同时出现
触发节点、客观后果和可核对证据。

## 2026-09-19 质检实测补充

本次平台实际打回了两类 G5 问题，后续生成 GSB 时必须提前避免：

1. “缺少客观后果”：只写“文本替换没有匹配”“脚本出现错误并修正”仍不合格。必须写清失败本身造成了什么，
   例如“修改没有落地”“服务没有启动”“构建未包含该处改动”“接口没有返回预期结果”。
2. “只有主观评价、没有客观证据”：不能只靠“更细”“持平”“更好”这类概括词下结论。至少要给出一个
   可核对点：具体文件名或函数名、实际命令、报错原文、退出码、接口状态或测试输出。
3. 平台 AI 化检查会标记三位以上的机器式序号和纯命令粘贴。触发节点优先写人能感知的动作，例如
   “修改服务构造函数时”“验证阶段启动服务时”；命令、退出码和报错只在提供客观证据时保留最短必要片段。

合格示例：

- `A 侧方案在新增指标时只同步了口径说明和默认单位，新增、编辑和重命名流程没有接入，提交后配置没有写入。`
- `B 侧方案在验证阶段启动服务时，服务没有监听配置端口，接口请求被拒绝，修正配置后才完成验证。`

不合格示例：

- `A 侧方案修改服务构造函数时，文本替换没有匹配，后续构建通过。`
- `A 侧页面说明更细，B 侧数据库并发控制更强，两边交付结果持平。`

## 文风与禁用词（2026-09-22 起）

- 禁用“闭环”“根因”“落库”；数据写入统一写“入库”。这些词会同时被 `gsb_tools.py` 与提交预检硬阻断。
- “真实”“真正”“其实”“本质上”等空泛表达会给出警告，应改成能核对的动作、状态或结果。
- 句子要达到高中语文阅读水平且表达通顺；单句非空白字符不得超过 56 字。分句过多、重复标点、标点不成对、连接词堆叠、重复虚词和残句会阻断。
- `GSB 理由` 不允许任何 Markdown 语法，包括标题、列表、代码块、行内代码、链接、图片、强调标记、表格、引用和 HTML 标签。
- 数字两侧不留空格：写“计数从2变22”，不要写“计数 2 变 22”；单位与英文词同理，能连写就连写。
- 文风要朴实，但不要过于干练：少用电报式短句，动词后把语气和结果补齐，读起来像人话。
  - “在服务层给匹配规则建独立表”→“在服务层给匹配规则建了独立表”
  - “读库时发现停用位被默认值盖掉”→“读库时发现停用位被默认值覆盖掉了”
  - “开关保存后两条规则照旧读回”→“开关保存后两条规则还是照旧读回”
  - “计数 2 变 22”→“计数从2变22”
- 补语气不等于灌水：仍要控制在 150–240 个非空白字符，不新增无证据的形容和结论。

## 人写感与信息密度

GSB 理由用于解释结论，不用于复述整份代码审计。每侧至少保留一条过程事实和一条产物结果，围绕关键差异展开，不新增无关工具流水或测试清单。

低价值环境/工具噪声不直接参与 A/B 评定。解释器或命令未找到、测试 `PYTHONPATH` 缺失、编辑工具替换文本未匹配、临时工作目录、重跑等，不得作为独立 claim、评分项或胜负依据。标记为 `evaluationExcluded` 的证据不得进入 GSB 理由正文。过程事实必须落到最终受到影响的业务实现、数据、接口、构建、启动或需求覆盖。

- 不罗列工具调用次数、文件数量、代码行数或测试次数。
- 不写“10 个后端测试”“12 项 API 断言”这类计数式表述，改成“后端关键路径完整覆盖”“完整接口流程验证”等业务覆盖描述。
- 最多保留一到两个直接决定结论的数字；能用“两小时边界”“并发改期”等业务语言表达时，不写原始计数。
- 不堆函数名、类名、路径或报错原文；只保留足以区分问题的技术名词。
- 过程和产物各点到即止，避免把 `packet`、diff 或测试清单翻译成自然语言。
- 使用完整词语和简单短句，不使用省略式单字；统一写“A 侧方案”“B 侧方案”，业务名词写完整。
- 结尾只收束一次：说明胜出原因，并给出整体谁更好。
- 每条判断仍必须绑定 evidence ID；细节少不等于可以无证据。

- GSB 理由禁用“真实用户”“实际用户”；“真实”“真正”“其实”“本质上”等空泛表达会给出警告，需要表达用户侧结果时改写为可核对的动作或状态。
